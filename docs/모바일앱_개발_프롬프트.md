# 모션브릿지 ERP — 모바일 앱 개발 프롬프트

> 아래 전체를 그대로 복사해서 AI(또는 개발자)에게 전달하세요.
> `[결정 필요]` 표시가 있는 항목은 먼저 정하고 넘기는 게 좋습니다 (문서 맨 아래 참고).

---

## 역할

너는 시니어 모바일 앱 개발자다. 이미 운영 중인 사내 ERP(웹 + REST API)에 붙는 **직원용 모바일 앱**을 만든다.
백엔드는 이미 있고 **수정 없이 그대로 쓴다.** 앱만 새로 만든다.

## 목표

법인카드를 쓰는 직원이 **휴대폰에서 지출 용도를 입력하고 제출**할 수 있게 한다.
지금은 PC 웹에서만 가능해서 직원들이 자리에 앉아야만 처리할 수 있다.
대표는 앱에서 **승인/반려**까지 할 수 있어야 한다.

레퍼런스는 고위드(Gowid) 법인카드 앱이다. 화면 구성과 흐름을 참고하되, 아래 API 스펙에 맞춘다.

---

## 1. 기존 시스템 (반드시 지킬 제약)

- **백엔드**: NestJS REST API. 기본 경로 `/api`.
  앱은 **사내/외부(모바일 데이터) 어디서나** 접속한다 → 운영 주소는 **HTTPS 도메인**이다.
  예: `https://erp-api.<회사도메인>/api`
  (서버 공개는 앱 개발과 별개의 선행 작업이다. 문서 맨 아래 **선행 작업** 참고)
- **인증**: JWT Bearer 토큰. `Authorization: Bearer <token>` 헤더.
- **권한(Role)**: `CEO`(대표) / `ADMIN`(관리자) / `EMPLOYEE`(직원)
  - 직원은 **자기 카드 지출만** 조회·수정 가능 (서버가 알아서 범위를 좁힘)
  - 승인·반려는 CEO 전용
- **금액**: 서버가 **원 단위 정수를 문자열로** 내려준다 (예: `"1913300"`).
  **절대 float/Number로 계산하지 말 것.** BigInt 또는 문자열 기반 정수 연산만 사용.
  화면 표시는 천단위 콤마 + "원" (예: `1,913,300원`).
- **시간대**: 서버·데이터 모두 `Asia/Seoul` 기준. 날짜 변환은 항상 KST로.
- **언어**: UI 전부 한국어. 존댓말, 간결한 문장.

## 2. 인증 흐름

```
POST /api/auth/login
body: { "email": "...", "password": "..." }
→ 200 { "accessToken": "...", "user": { id, name, email, department, roles } }
```

- 토큰은 기기 보안 저장소에 보관 (iOS Keychain / Android Keystore — `AsyncStorage` 같은 평문 저장 금지)
- 만료는 12시간. **401을 받으면 토큰을 지우고 로그인 화면으로 보낸다.**
  - 앱은 외부망에서도 쓰므로, 만료됐다고 작업 중이던 입력을 날리지 말 것.
    재로그인 후 **원래 화면과 입력값으로 되돌아간다.**
  - 12시간 만료는 모바일에서 하루 두 번 로그인해야 한다는 뜻이다 → `[결정 필요 D]` 참고
- 로그인 실패 5회 시 서버가 10분 잠금 후 **HTTP 429**를 준다 → "로그인 시도가 너무 많습니다" 안내 표시
- 내 정보: `GET /api/auth/me` → `{ id, name, email, department, roles, effectiveScope: { isCeo, isAdmin, ... } }`
  - **화면 분기는 `effectiveScope.isCeo` / `isAdmin`으로 한다.**
- 비밀번호 변경: `POST /api/auth/change-password` body `{ currentPassword, newPassword }` (새 비밀번호 8자 이상)

## 3. 화면 명세

### 3-1. 로그인
- 이메일 / 비밀번호 / 로그인 버튼만.
- **계정이나 비밀번호 예시를 화면에 절대 표시하지 말 것.**

### 3-2. 홈 — 내 카드 (레퍼런스 1번 화면)

- 상단: 미제출 건수 알림 배너
  → "아직 제출하지 않은 지출이 N건 있어요" + [지금 제출하기] → 일괄 제출 화면으로 이동
- 내 카드 목록. 카드마다:
  - 발급사 + 별칭 + 뒤 4자리 (예: `신한 2597`)
  - **이번 달 이용금액** (크게)
  - 발급사별 브랜드 색 구분 (웹의 `CardBrandMark`와 동일 규칙)

```
GET /api/cards
→ [{ id, name, issuer, cardType, last4, holderUserId, holder: {id, name}, isActive, pendingCount }]

GET /api/cards/expenses?from=YYYY-MM-DD&to=YYYY-MM-DD&take=500
→ { summary: { all, notSubmitted, submitted, confirmed, excluded } , rows: [...] }
   각 summary 항목 = { count: number, amount: string }
```

> ⚠️ **잔여한도는 지금 불가.** 카드 테이블에 한도 필드가 없다.
> 레퍼런스의 "잔여한도"를 넣으려면 백엔드 스키마 변경이 필요하다 → `[결정 필요 A]`

### 3-3. 지출 상세 / 용도 입력 (레퍼런스 2번 화면)

지출 1건을 열어 용도를 넣고 제출한다.

- 상단: 가맹점명(`storeName`), 금액(크게)
- 정보: 결제일시(`usedAt`), 결제카드(카드 별칭 + last4), 승인상태(`status`)
- **용도** (필수): 칩(chip) 선택 방식. 목록은 아래 참고
- 메모 (선택): 자유 입력
- [제출하기] 버튼

```
PATCH /api/cards/expenses/:id/purpose
body: { "purposeText": "점심식비", "memo": "팀 점심" }
→ 이 호출 하나로 용도 저장 + 상태가 SUBMITTED(제출됨)로 바뀐다.
```

**용도 목록**은 코드값에서 가져온다:
```
GET /api/code-values
→ kind === 'CARD_PURPOSE' 인 항목의 { code, label } 사용
```
코드값이 비어 있으면 아래 기본 목록을 쓴다:
`식비, 회식비, 업무교통비, 야근교통비, 국내출장비, 국외출장비, 접대비` 등 (웹의 `DEFAULT_PURPOSES` 참고)

### 3-4. 간편 일괄 제출 (레퍼런스 3번 화면) — **핵심 화면**

미제출 지출을 **날짜별로 묶어** 한 화면에서 여러 건 제출한다.

- 날짜 헤더(예: `2026.08.11 (목)`) 아래에 그 날 지출들
- 각 행: 시각 · 가맹점명 · 금액 · 용도 칩(인라인 선택)
- 용도를 고른 행만 카운트 → 하단 고정 버튼 [N건 제출하기]
- 제출은 건별로 `PATCH .../purpose`를 반복 호출 (일괄 제출 API는 없음)
  - **일부 실패해도 성공한 건은 유지**하고, 실패 건수와 사유를 명확히 보여줄 것

```
GET /api/cards/expenses?status=PENDING,REJECTED&take=200
```
- `status`는 쉼표 구분 다중 지정 가능
- **반려(REJECTED)된 건은 눈에 띄게 표시**하고 `rejectReason`을 함께 보여준다 (재제출 대상)

### 3-5. 승인함 (CEO 전용)

`effectiveScope.isCeo === true` 일 때만 노출.

- 승인 대기 목록: `GET /api/cards/expenses?status=SUBMITTED&take=200`
- 건별 승인: `POST /api/cards/expenses/:id/confirm`
- 건별 반려: `POST /api/cards/expenses/:id/reject` body `{ "reason": "사유" }`
- 일괄 승인: `POST /api/cards/expenses/confirm-bulk` body `{ "ids": ["...", "..."] }`

### 3-6. 내 정보
- 이름 / 이메일 / 소속 부서 / 권한 표시
- 비밀번호 변경
- 로그아웃 (토큰 삭제)

## 4. 데이터 모델 참고

`GET /api/cards/expenses` 의 `rows[]` 주요 필드:

| 필드 | 타입 | 설명 |
|---|---|---|
| `id` | string | |
| `cardId` | string | |
| `usedAt` | string(ISO) | 결제일시 |
| `amount` | string | **원 단위 정수 문자열** |
| `storeName` | string \| null | 가맹점명 |
| `status` | enum | `PENDING`/`SUBMITTED`/`CONFIRMED`/`REJECTED`/`EXCLUDED` |
| `purposeText` | string \| null | 용도 |
| `memo` | string \| null | |
| `rejectReason` | string \| null | 반려 사유 |
| `isCancelled` | boolean | 취소 거래 |
| `card` | object | 카드 정보 (별칭·소지자 등) |

**상태 흐름**
```
PENDING(미제출) ──용도 입력──▶ SUBMITTED(승인 대기) ──▶ CONFIRMED(승인 완료)
      ▲                                    │
      └──────────── REJECTED(반려) ◀────────┘
EXCLUDED(카드지출 아님) — 앱에서는 목록에서 숨긴다
```

- `isCancelled === true` 이거나 `status === 'EXCLUDED'` 인 건은 **목록에서 제외**한다.

웹과 같은 톤을 유지한다 (따뜻한 중성색 + 주황 브랜드).

```
브랜드 주황   #f5911e   (진한 톤 #b45f05)
본문 먹색     #2a2724   (보조 #57514b / 흐림 #857d75)
선·배경       #eae5e0 / #f5f2ef / #faf8f6
긍정(입금)    #2f8f5b      부정(출금·반려)  #cf4b3c      주의  #c9820f
```

- 폰트: Pretendard
- 금액은 숫자 폭이 일정한 글꼴로, 천단위 콤마 필수
- 터치 영역 최소 44×44pt
- **한 손 조작 전제**: 주요 버튼(제출하기 등)은 화면 하단 고정
- 다크모드는 이번 범위에서 제외

## 6. 기술 스택 (권장)

- **React Native + Expo** + TypeScript
  - 이유: 웹이 이미 React/TypeScript라 타입·유틸(금액 포맷 등)을 재사용하기 쉽다
- 상태·서버 통신: TanStack Query (재시도·캐시·낙관적 업데이트)
- 토큰 저장: `expo-secure-store`
- 대안으로 Flutter도 가능하나, 기존 코드 재사용 이점은 사라진다

## 7. 반드시 지킬 것

1. **금액을 float로 계산하지 않는다.** 문자열/BigInt 정수 연산만.
2. **모든 쓰기 동작에 실패 처리를 붙인다.** 실패했는데 조용히 넘어가면 안 된다.
   (성공/실패 건수와 사유를 사용자에게 반드시 보여줄 것)
3. **오프라인·통신 실패**를 가정한다. 제출 중 끊기면 무엇이 저장됐고 무엇이 아닌지 알려준다.
4. **401 → 로그인 화면**, **429 → 잠금 안내**로 분기한다.
5. 화면에 **계정·비밀번호·토큰을 절대 노출하지 않는다.** 로그에도 남기지 않는다.
6. 서버 응답의 `EXCLUDED`·취소 건은 사용자에게 보여주지 않는다.
7. API 주소는 **빌드 설정(dev/prod)으로 분리**한다. 코드에 하드코딩 금지.

### 외부망에서 쓰기 때문에 추가로 지킬 것

8. **평문 HTTP를 절대 허용하지 않는다.**
   - Android: `usesCleartextTraffic=false` (기본값 유지, 예외 도메인 추가 금지)
   - iOS: ATS 예외(`NSAllowsArbitraryLoads`) 추가 금지
   - 개발 중 로컬 API를 쓸 때만 dev 빌드에 한해 예외를 두고, **운영 빌드에는 절대 넣지 않는다.**
9. **모바일 데이터 환경을 전제한다.** 지연·끊김이 잦다.
   - 요청 타임아웃을 명시(15초 권장)하고, 조회 실패는 재시도 버튼을 준다
   - **쓰기 요청(제출·승인)은 자동 재시도하지 않는다** — 중복 제출 위험. 사용자가 직접 다시 누르게 한다
   - 목록은 캐시해서 오프라인에서도 마지막 조회 내용을 보여주되, **"오프라인 · 마지막 조회 시각" 표시**를 붙인다
10. **회사 밖에서 열리는 화면**임을 감안한다.
    - 앱 전환(백그라운드) 시 스크린샷 미리보기에 금액이 남지 않도록 가림 처리
    - 일정 시간(예: 15분) 미사용 시 자동 잠금 후 재인증 (생체인증 사용 권장)

## 8. 완료 기준

- [ ] 직원 계정으로 로그인 → 내 카드와 이번 달 이용금액이 보인다
- [ ] 미제출 건이 날짜별로 묶여 보이고, 용도를 골라 여러 건을 한 번에 제출할 수 있다
- [ ] 제출 후 상태가 "승인 대기"로 바뀌고, 미제출 건수 배지가 줄어든다
- [ ] 반려된 건은 사유와 함께 눈에 띄게 표시되고 재제출할 수 있다
- [ ] 대표 계정으로 로그인하면 승인함이 보이고 승인·반려·일괄승인이 된다
- [ ] 통신 실패·토큰 만료 상황에서 앱이 죽지 않고 적절히 안내한다
- [ ] PC 웹에서 본 숫자와 앱의 숫자가 정확히 일치한다
- [ ] **사내 와이파이를 끄고 모바일 데이터만으로** 로그인·조회·제출이 모두 된다
- [ ] 비행기모드에서 앱을 열면 마지막 조회 내용과 "오프라인" 표시가 뜨고, 죽지 않는다
- [ ] 제출 도중 통신이 끊겼을 때 무엇이 저장됐는지 정확히 알려준다
- [ ] 운영 빌드에 평문 HTTP 예외가 들어 있지 않다

# 시작 전 결정해야 할 것

## [결정 필요 A] 카드 잔여한도 표시 여부
레퍼런스 화면에는 "잔여한도 73,214,200원"이 있지만, **현재 DB에 카드 한도 필드가 없다.**
- **넣지 않는다** → 이번 달 이용금액만 표시. 앱만 만들면 됨 (권장)
- **넣는다** → `CorporateCard`에 월 한도 필드 추가 + 마이그레이션 + 웹 관리 화면 필요

## [결정 필요 B] 영수증 사진 첨부
레퍼런스는 "영수증"이 핵심이지만, **현재 시스템에 파일 첨부 기능이 전혀 없다.**
- **넣지 않는다** → 용도·메모만 입력 (권장, 지금 흐름 그대로)
- **넣는다** → 파일 저장소·업로드 API·용량 정책까지 새로 설계해야 함 (작업량 큼)

## [결정 필요 D] 로그인 유지 기간 (모바일 UX)
현재 토큰 만료는 **12시간**이고 갱신(refresh) 구조가 없다.
모바일에서는 **하루 두 번 로그인**해야 한다는 뜻이라 실사용에서 불편이 크다.
- **그대로 둔다** → 앱 작업량 없음. 대신 재로그인이 잦다
- **모바일 만료를 늘린다** (예: 7일) → 백엔드 `JWT_EXPIRES_IN` 조정. 간단하지만 **토큰 탈취 시 위험 구간이 길어진다**
- **refresh 토큰을 도입한다** (권장) → 짧은 access + 긴 refresh. 백엔드 작업 필요하지만 보안·편의 둘 다 챙김

> 외부망에서 쓰는 앱이므로 "만료를 무작정 길게"는 권하지 않습니다.
> 생체인증 잠금(위 9~10번)과 함께 refresh 토큰을 넣는 쪽이 안전합니다.

# 선행 작업 — 서버를 외부에서 접속 가능하게 (앱보다 먼저)

**결정됨: 사내 와이파이 밖(모바일 데이터 포함)에서도 접속한다.**
지금 API는 사무실 PC의 `localhost:4000`에서만 돌기 때문에, **앱 개발 전에 이 작업이 선행되어야 한다.**
이건 앱 개발과 별개의 인프라 작업이며, 담당자가 다를 수 있다.

## 필수 요건

1. **HTTPS 도메인** — 자체 서명 인증서 불가(모바일에서 차단됨). Let's Encrypt 등 정식 인증서 필요
2. **DB는 절대 인터넷에 노출하지 않는다** — PostgreSQL 5432 포트는 외부에서 닫는다. API만 공개
3. **CORS 허용 목록 갱신** — 서버 `.env`의 `CORS_ORIGINS`에 새 웹 주소 추가
   (앱은 Origin을 보내지 않아 CORS 대상이 아니지만, 웹은 영향받는다)
4. **방화벽** — 443만 열고 나머지는 닫는다. SSH는 키 인증만
5. **백업** — 서버 이전 시 DB 백업 경로가 바뀐다. 자동 백업(`scripts/backup.ps1`)이 새 환경에서도 도는지 확인

## 방식 선택지

| 방식 | 장점 | 단점 |
|---|---|---|
| **Cloudflare Tunnel** | 지금 PC 그대로 두고 HTTPS 확보. 고정 IP·포트포워딩 불필요. 무료 | PC가 켜져 있어야 함 |
| **클라우드 VPS 이전** (AWS/네이버클라우드 등) | 24시간 가동, 사무실 정전·PC 문제와 무관 | 서버·DB 이전 작업, 월 비용 |
| **포트포워딩 + DDNS** | 추가 비용 없음 | **권장하지 않음** — 홈/사무실 회선을 직접 노출, 보안 부담 큼 |

> **처음이라면 Cloudflare Tunnel**이 부담이 적습니다. PC를 계속 켜두는 게 부담이면 VPS 이전이 맞습니다.

## ⚠️ 공개 전에 반드시 닫아야 할 보안 항목

인터넷에 노출되는 순간 아래는 "나중에"가 아니라 **선결 조건**이 된다.
(모의 해킹 훈련 대상이 된다면 더더욱)

- [ ] **대표 계정 비밀번호 변경** — 아직 시드 초기값(`changeme123!`)이며 저장소에 그대로 적혀 있다
- [ ] **라우트 가드 통일** — `/treasury`·`/pnl`·`/journal`은 메뉴에서만 숨겨져 있고 URL 직접 접근 시 화면이 뜬다
      (데이터는 API가 403으로 막지만, 화면 구조가 노출된다)
- [ ] **미사용 계정 정리** — `admin@`, `staff@` 등 시드 계정 비활성화
- [ ] **로그인 실패 감사 로그** — 현재 침입 시도 기록이 남지 않는다
- [ ] **요청 전반 rate limit** — 지금은 로그인에만 걸려 있다
- [ ] **서버 접근 로그 보관·모니터링**

> 이미 적용된 것: JWT 위조 차단, 입력 검증 우회(mass assignment) 차단, CORS 허용 목록,
> 로그인 무차별 대입 잠금, 보안 헤더, 회사 경계 검사.
